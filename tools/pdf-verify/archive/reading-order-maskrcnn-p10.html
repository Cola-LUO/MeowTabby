连线走：PDF 阅读序到底怎么排

以 Mask R-CNN（arXiv:1703.06870v3）第 10 页为例。20 个参与排序的块、612×792 画布、y-up 坐标。每一步都在这页真实数据上复算：walkReadingOrder()。

Step 1 / 5

先编号，但不按编号排序

每个块先拿一个 cid：文本块按 minOrder（它认领到的最小文本项在内容流里的位置）升序；keep 块（图、表、公式）的 paras 为空，一律排到末尾，同分再按几何 (t 降序, l 升序)。

本页 18 个有文本的块 minOrder 是 84 → 283，cid 正好 0..17；两张表拿到 cid 18 / 19。注意左表的 minOrder 是 0——内容流里它最靠前，但它其实在页首，所以 cid 不能直接当阅读序。

cid 在后面只做一件事：判断两个块是不是 同排且紧挨（R1 的 A.cid + 1 === B.cid）。它不负责全局次序。

Step 2 / 5 · R1

同排线：先把“一行里的左右块”串起来

R1 只认三个条件同时成立：cid 相邻、A 严格在 B 左边（A.r + ε < B.l）、竖直重合度 > 0.8。本页只连出一条：左表 → 右表。

为什么需要它？双栏页里同一水平带有左右两块；如果没有 l2r，R2 会让上方块同时连到左右两个下方块。有了 l2r，R2 只需连到这一排最右边的块，再由 l2r 负责横向接力。 

// R1：cid 紧挨 + 严格在左 + 竖直重合
if (A.cid + 1 === B.cid
    && A.r + EPS < B.l
    && verticalIoU(A, B) > 0.8) {
  l2r.set(i, j); r2l.set(j, i)
}
Step 3 / 5 · R2 + R3 + R4

上下线：只连“中间没东西挡着”的邻居

R2 的条件是：A 严格在 B 上方（A.b + ε > B.t）、A 与 B 左右压到、并且 R3 挡道检查通过——A 与 B 之间不能有第三个块 W 同时满足“水平压到 A 或 B、且 A 的底 > W 的顶、W 的底 > B 的顶”。

这一步把“隔着一个题注/图/段落的两个块”全部拆开。本页 18 → 1 就被 0（Table 8 题注）挡住：表格底边 642.4 只比题注顶边 640.4 高 2px，刚好够 R3 判定“中间有人”。

R4 加宽重试：同栏块常因缩进、标题短而左右边缘差几个像素，导致“压不到”。若边缘差 ≤ 0.155 × 页宽（本页 94.9px），就把 l/r 撑到与上下邻居对齐，再跑一次 R2；撑宽后若与任何原始框双轴相交，整块放弃。本页 12 个块被轻微撑宽，最大 28.8px，把断掉的链补了回来。

结果：左栏 0→1→…→7，右栏 8→9→…→17，右表 19 同时指向 0 与 8。

Step 4 / 5 · R5 + R6

入口 + 深度优先走线

入口是 up 为空的块。本页只有一个：18（左上表）。多个入口时按 R5 比较器排：水平压到就“更靠上先读”（b 大的在前），否则“更靠左先读”（l 小的在前）。

走线从入口开始，沿 dn 深度优先；每个子节点先 walkUp 找到它未访问的祖先；走不动就弹栈回溯。本页轨迹：

18 → 19 → 0 → 1 → … → 7 →（回溯）→ 8 → 9 → … → 17

19 的 dn 排序是 [0, 8]：0 在左（l=49.3），8 在右（l=307.9），所以先走完整条左栏再回右栏。这不是按栏分组的结果，而是 DFS 栈的顺序——也是本页 Table 9 的说明被排到左栏之后的原因。

Step 5 / 5

排完序 ≠ 全部编号

排序产出 20 个块，但上游只给 plain text + title 编号；table、figure、caption、公式在序列里占位不占号——它们决定前后正文的编号次序，自己不出现在编号序列里。

本页实际：plain text 13 个 + title 3 个 = 16 个编号；2 个 table、2 个 table_caption 只占位。编号是跨页连续累加的，这里显示的是“本页局部序号”，方便对照。

这也解释了为什么排序层要收 keep 块：它们虽然不编号，但必须参与 R3 挡道与 R6 走线，否则图/表挡不住上下直连。

为什么不能直接按 y 排序？

双栏页的左右栏在同一高度上各有一块：左栏底块 cid 7 与右栏底块 cid 17 的 t 只差 0.1。按 y 排会左右横跳；按“先左栏再右栏”又需要先知道栏边界。连线法不猜栏，只连几何上真的相邻的块。

为什么不能按 cid 排序？

cid 是 PDF 内容流，不是版面。左表的 minOrder 是 0（文本流最先出现），但它在页首；图表类 keep 块还会被一律排到 cid 末尾。cid 只在 R1 里当“同排紧挨”的局部证据。

和旧算法差在哪？

旧臂 groupColumns() 只拿 plain text 候选，用“向上扫描找栏间空白”的方式归栏，再逐栏拼接；图/表不参与，所以挡不住上下直连。新臂把 keep 块放进节点集，用 R3 当障碍，这正是“图下面那段被隔开的正文”不再直连的原因。
