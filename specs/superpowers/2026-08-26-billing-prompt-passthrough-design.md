# MeowTabby × billing-backend：前端提示词透传与全托管 AI 切换 — 设计文档

- 日期：2026-08-26
- 状态：已与需求方逐节确认（接口契约 / 闸门规则 / 后端 / 前端 / 账户流 / 测试上线）
- 涉及仓库：`/Users/Luo_F/vs_code/billing-backend`（后端，Python/FastAPI）、`/Users/Luo_F/vs_code/MeowTabby`（前端，WXT 浏览器扩展）
- 方案：方案 A —— 单一通用流式端点 + 前端托管适配器（对比过的备选：B 按功能多端点，否决；C OpenAI 兼容代理，否决，理由见 §13）

## 1. 背景与目标

billing-backend 当前只接受 `text + target_lang + source_lang`，提示词完全在服务端拼装（固定 `SYSTEM_PROMPT` + 包装语）。MeowTabby（Read Frog 系扩展）拥有完整的提示词体系：内置模板、用户自定义提示词、批量规则、网页上下文占位符替换，且现有托管/本地两条通道发出的都是**已组装完成**的 `systemPrompt + prompt` 两段式终稿。前端目前没有任何调用 billing-backend 的代码。

本设计的目标：

1. 前端把自带提示词（已组装终稿）作为参数传给 billing-backend；后端改为原样接收、不再拼装提示词（一步切换，不留双通道）。
2. MeowTabby 的**全部托管 AI 功能**（网页翻译、选词/输入框翻译、字幕翻译及字幕切分、摘要生成、语言检测）切换到 billing-backend，契约必须通用。
3. 前端流式体验保持不变：后端新增 SSE 流式能力。
4. 前端实现完整账户流（注册/验证码/登录/会话/余额）。
5. 免费通道（DeepL/DeepLX 等）与用户自定义能力（BYOK、自定义提示词）原样保留；billing-backend 是在原体系上**叠加**的付费托管服务。

## 3. 接口契约

### 3.1 端点

`POST /v1/generate` —— SSE 流式；鉴权 `Authorization: Bearer <session_id>`（沿用现有会话体系）。翻译、字幕、摘要、语言检测全部走此端点。现有 `POST /translate` 退役（见 §5.5 删除清单）。

### 3.2 请求体（pydantic 校验）

| 字段                | 类型   | 约束                         | 说明                                                                                                                                                                                    |
| ------------------- | ------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `request_id`        | string | 必填，≤64 字符               | 计费幂等键；前端每次真实模型调用铸造新的，自动重试复用同一个                                                                                                                            |
| `feature`           | string | 必填，≤64 字符               | 功能标签，服务端只存储不解析：`pageTranslation` / `selectionTranslation` / `inputTranslation` / `videoSubtitles` / `videoSubtitlesSegmentation` / `languageDetection` / `summarization` |
| `system_prompt`     | string | 必填，1–4000 字符            | 前端已组装完成的系统提示词                                                                                                                                                              |
| `prompt`            | string | 必填，1–20000 字符           | 前端已完成占位符替换的用户提示词（含待处理文本）                                                                                                                                        |
| `max_output_tokens` | int    | 可选，默认 4096，范围 1–8192 | 输出封顶，透传给模型的 `max_tokens`                                                                                                                                                     |

长度上限是计费安全参数：凡是会进入模型输入的内容必须有上限（同 F23 对语言字段立下的规矩）。4000/20000 按最坏 2 token/字折算、不突破模型上下文窗口推得，评审阶段可依据真实批量数据微调。

### 3.3 响应

流开始**前**出错：普通 HTTP 状态码 + JSON（401/402/422/429/503 等），与现有风格一致。

流开始后为 SSE 事件：

- `event: delta`，`data: {"text": "..."}` —— 增量文本；
- `event: done`，`data: {"usage": {...}, "cost": <元>, "latency_ms": <int>}` —— 成功结束（结算完成后发出）；
- `event: error`，`data: {"detail": "..."}` —— 中途失败（上游错误、结算异常等），随后关闭连接。

实现备注：流中每 ~15s 发一个 SSE 注释心跳，防代理掐空闲连接；`done` 在结算完成后发出。

### 3.4 幂等语义

- `request_id` 已完成 → 重放缓存结果（单个 `delta` 携带全文 + `done`），**不重复扣费**；
- `request_id` 在途 → 409；
- `request_id` 对应失败（上游失败/被取消）→ 缓存行作废，同 id 允许作为新请求重入；
- 缓存落 SQLite 表 `idempotency_cache`（跨重启有效），TTL 600s，访问时惰性清理。

## 4. 计费闸门与结算规则（D8，正式变更旧裁定）

**新规则：**

1. 排队后取**新鲜**余额快照（沿用 F42/F50 的接线与排序要求，在工作线程执行）；
2. 余额 > 0 → 放行；余额 = 0 → 402（前端收到后取消该页剩余队列并提示充值）；
3. 结算按**真实** usage 走现有 `charge_and_log`：余额足够全额扣；不足则扣到 0、译文照常交付、差额记 `settle_partial` 审计（现有 F8 机制，不改）；
4. 同一用户在途并发上限仍为 1（F20 不改），因此单用户最大敞口 = 一批的真实成本。

**敞口量化**：单批最坏 ≈ (4000+20000)×2 token × cache_miss 单价 + 8192 completion × 单价 ≈ 0.08 元；典型批（≤1000 字）约 0.003–0.005 元。且余额>0 必然来自真实充值，套利成本高于收益。

**被替代的旧裁定**：`estimate_max_cost` 估算闸门（F2）及其上界证明义务（含 `+60` 余量、F23 的语言字段计入）不再承担资金安全职能，估价机器整体退役（§5.5）。资金安全改由"单批敞口有界 + 在途=1 + 扣到零钳制 + 真实 usage 结算"承担。此为本设计对既有裁定的**正式变更**，交付对抗评审重新裁定。

## 5. 后端改造（billing-backend）

### 5.1 `POST /v1/generate` 生命周期

1. `require_session` 鉴权（不改）；
2. 幂等检查（§3.4）；
3. 取用户信号量（在途=1，超限 429；F20 逻辑不改，但信号量持有延伸至"流结束 + 结算完成"）；
4. 工作线程内取新鲜余额快照，=0 → 402；
5. 以流式模式调用上游（`stream=True`、`stream_options={"include_usage": true}`），逐块转发为 `delta` 事件；
6. 流结束（或客户端掉线后由后台任务收尾，见 §5.2）：取真实 usage → `charge_and_log` 结算；
7. 发 `done` 事件（含账单），释放信号量。

超时参数：等待首块 ≤60s；单次调用总时长 ≤120s（对齐前端 `MAX_BATCH_TIMEOUT_MS`）。

### 5.2 客户端掉线

后端**不**跟随掐断：开后台任务把上游流消费到底，照常结算扣费，审计行正常落库。杜绝"掉线逃单"；上游成本已实际发生，由发起者承担。

### 5.3 取消（D9）：`POST /v1/cancel`

- 请求体 `{"request_id": ...}`，Bearer 鉴权，只能取消自己的在途单；
- 效果：立即关闭与上游的连接（越早掐，生成的字越少，成本越小）；已生成部分按真实 usage 结算；
- 该 `request_id` 在幂等缓存中标记失败（作废），前端可用新 id 重发；
- 取消不在途/不存在的单 → 幂等无副作用的 200。

### 5.4 账户接口改验证码制（D10）

- `POST /register`：建未激活账户 + 发送 6 位数字验证码（哈希存储，10 分钟有效）；邮件模板改为纯文字验证码，无链接；
- 新增 `POST /verify-code {email, code}`：核对通过即激活；每邮箱 10 分钟内最多尝试 5 次（新增限流器），用后即废；
- `POST /resend-verify`：重发新码（沿用现有限流 3 次/10 分钟）；
- `POST /forgot-password`：发验证码（不再发链接）；
- `POST /reset-password`：入参改为 `{email, code, new_password}`；重置后吊销全部旧会话（不改）；
- 删除 `GET /verify`（链接端点）；
- 邮件配置不再依赖 `APP_BASE_URL`（无链接可发）。

### 5.5 删除清单（一步切换，D3）

- `POST /translate` 端点与 `TranslateReq`；
- `SYSTEM_PROMPT`、`build_user_prompt`（服务端提示词拼装全灭）；
- `estimate_max_cost` 及其配套上界证明（§4）；
- `GET /verify` 链接端点。

### 5.6 数据与配置变更

- `usage_log` 新增列 `feature TEXT`（init_db 沿用现有补列迁移风格）；`source_text` 存用户 `prompt`（截断 4000 字符），`translation` 存模型输出全文；
- 新表 `idempotency_cache(user_id, request_id, status, result_json, created_at)`，PK `(user_id, request_id)`；
- 输出上限：常量改为按请求的 `max_output_tokens`（默认 4096，硬上限 8192）。

### 5.7 不动清单

注册/登录/会话体系骨架、充值/退款管理接口、`/me`、`/stats`、邮件发送框架、三层成本公式、部分结算钳制（F8/F27）、token 哈希（F17）、限流器、`_DS_POOL` 线程池隔离（F15/F22）、鉴权类修复（F12/F32）。

## 6. 前端改造（MeowTabby）

**总思路：只换"系统托管"分支的运输层，其余一律不动。**

### 6.1 运输层替换

- 背景服务的托管分支（现经 oRPC 打 readfrog）替换为对 billing-backend 的 SSE 请求：`fetch` + ReadableStream 解析 `delta/done/error`；
- 解析出的增量塞进**现有** background-stream 消息通道（`chunk`/`done`），页面渲染侧零改动；
- 请求体组装：现有 `promptResolver` 产出的 `systemPrompt`/`prompt` 原样作为 `system_prompt`/`prompt`；`requestId` 沿用现有铸造逻辑（每次真实调用新 UUID，自动重试复用）；`feature` 按当前路由映射（摘要子调用标 `summarization`，其余按 `HostedAiTextStreamRoute` 原值）。

### 6.2 配置

新增后端地址配置（环境变量，默认指向部署地址），托管分支不再使用 readfrog 地址；readfrog 账户相关（better-auth、`orpc.billing.status`）由 billing 账户体系替代（§7）。

### 6.3 错误分级

- 402 → 取消该页面剩余全部批次 + 充值引导；
- 401 → 清本地会话 + 重新登录引导；
- 502/超时 → 现有 `RequestQueue` 自动重试（复用 `request_id`，后端幂等兜底）。

### 6.4 并发对齐

计费通道的 `RequestQueue` 速率强制为 1（对齐后端在途=1）；批次大小参数不动。

### 6.5 取消联动（D9）

用户取消翻译：前端排空队列（现有能力）→ 对在途批调用 `POST /v1/cancel` → 中止本地流读取。

### 6.6 不动清单

BYOK/本地模型通道、DeepL/DeepLX 免费通道、提示词组装与自定义配置、批量队列/缓存/重试的既有逻辑、内容侧渲染。

## 7. 账户流（前端界面，D4/D10）

1. **账户菜单换芯**：现 readfrog 账户菜单替换为 billing 账户——未登录显示登录/注册入口；已登录显示邮箱、余额（`/me`）、充值入口、退出；
2. **注册表单**：昵称 + 邮箱 + 密码 → 发送验证码 → 表单内填码激活；"没收到"入口触发重发；
3. **登录表单**：邮箱 + 密码；
4. **找回密码**："忘记密码" → 邮箱收码 → 填码 + 新密码；
5. **会话存储**：`session_id` 存 `chrome.storage.local`（背景服务管理），请求自动携带；退出登录调 `/logout` 并清本地；
6. **充值入口（v1 从简）**：仅引导页/联系方式（后端充值为管理员手动接口）；自助支付为后续切片；
7. **401 统一处理**：任何请求收到 401 即清会话并提示重新登录。

## 8. 安全设计汇总

- 提示词长度上限 + 全量计入模型输入约束（防 F23 类绕过）；
- 掉线仍消费完上游并结算（防掉线逃单）；
- 幂等重放不双扣、在途 409（防重试双扣）；
- 验证码：哈希存储、10 分钟过期、5 次尝试锁定、用后即废（6 位码 10^6 组合，限次后暴力不可行）；
- 取消只能作用于本人在途单（session 鉴权）；
- 在途=1 + 新鲜余额快照（F20/F42/F50 语义保留）。

## 11. 已知局限（坦承，不在本次范围）

- 限流/并发/信号量仅单进程有效（既有裁定的已知局限，多 worker 需共享存储）；
- 充值仅管理员手动，无自助支付；
- 幂等缓存 600s，超窗重试视同新单（前端重试窗口远小于此）；
- `max_output_tokens` 上限 8192，超长字幕切分场景需实测确认。

## 13. 备选方案与否决理由

- **方案 B（按功能多端点）**：N 个端点重复 N 遍计费流水线，与"契约通用"决策冲突。否决。
- **方案 C（OpenAI 兼容流式代理）**：前端最省（复用 BYOK 管道），但后端需把对抗评审过的 `call_deepseek → 结算` 核心区整体重写为代理，幂等/功能标签只能塞自定义头，评审风险显著更高。否决。
- **选定方案 A**：计费内核保持原样、增量扩展，契约原生携带幂等键与功能标签；前端新增的 SSE 消费代码隔离在托管分支内。
