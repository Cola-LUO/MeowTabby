## 1. 目标与已确定的要求

以 MeowTabby 为唯一维护项目，把 pdf-verify 的 D 方案作为正式 PDF 底层实现，替换 MeowTabby 对应的旧处理代码。正式扩展与内部验证工具直接调用同一份核心代码和处理流程。

用户已明确：

- 正式扩展采用 D，验证器也只采用 D。旧、A、B、C 的可执行分支、开关和方案对比全部删除。
- PDF 文字提取、模型检测、坐标统一、补框、文字归属、分行分段、阅读序、跨栏和跨页同段判断，以当前 pdf-verify 的 D 路径为基准。
- MeowTabby 的产品界面与交互保留，翻译请求、计费、译文排版和导出继续使用现有产品能力。
- 译文位置来自 PDF 文字整理为行、段后的包络。跨栏、跨页回填沿用 MeowTabby 现有容量分配和放置规则。
- 边处理边翻译，只等待末尾可能接续的组；按 PDF 页码顺序送出，后面的内容不能越过待确定的前文。
- 验证工具及其仍需保留的功能迁入 MeowTabby，但不进入正式扩展安装包。
- 合并验收后，原 pdf-verify 不再承担任何运行依赖；处理其目录前保留可恢复的 Git 历史。

这里的“保留完整验证功能”已按用户后续决定收窄：保留 D 的验证能力与资料，删除多方案选择和旧方案对比。

## 2. 当前代码事实

### 2.1 本次检查的基线

- pdf-verify：`4dc59665c91e60b6b6476a94db6ae56eba103601`。
- MeowTabby：`be874fe73deeb9dd5f987a768a9dc851dd6d5336`。
- 检查时两边 Git 工作区均无改动。实施前重新核实，不能把本文的提交号当作自动覆盖后续改动的理由。
- PDF.js 均为 `4.10.38`，ONNX Runtime 均为 `1.20.1`，WXT 均为 `0.21.4`。

### 2.2 算法与调度差异

pdf-verify 的 D 由入口组合而成：启用 `assignItems` 的 `splitHanging`，启用阅读序的公式扩宽限制，扁平配对使用修改后的权重及阈值。当前验证器默认选 C，因此基线采集必须显式执行 D。

MeowTabby 目前先做页内配对，再用 `decideCrossPage` 单独判断跨页。验证器按各页阅读序生成全局正文序列，再由 `planFlatMerges` 统一判断相邻正文块。两条判断流程不能并存。

MeowTabby 由 `IntersectionObserver` 触发处理，队列顺序来自可见事件，而非页码。翻译调度器只接收文字数组，按调用先后排队，最多两批在途，不校验页码。因此现有串行推理队列不能保证按页码送翻。

现有译文回填已经共用容量分配逻辑，但其输入连接仍区分页内组和双成员跨页组。D 的组可跨多个栏、多个页面，需要改连接方式。

### 2.3 主要取证文件

- `src/entrypoints/pdf-translate/main.ts`：MeowTabby 页面调度、旧处理流程与产品接入。
- `src/entrypoints/pdf-translate/modules/translate/scheduler.ts`：现有翻译并发、缓存和在途去重。
- `src/entrypoints/pdf-translate/modules/viewer/render-view.ts`：段落分簇与包络译文盒。
- `src/entrypoints/pdf-translate/modules/viewer/trans-units.ts`：送翻单元和合并组回填。
- 原项目 `src/entrypoints/pdf-verify/main.ts`：D 实际执行步骤及验证功能。
- 原项目 `src/modules/assign/`：文字归属、切段、阅读序及扁平配对。

本节是代码事实。后续各节是建议采用的合并设计，并非现有代码已经具备的能力。

## 3. 代码组织与构建边界

### 3.1 推荐结构

在 MeowTabby 内建立以下边界，最终文件细分在实施计划中列出：

```text
src/modules/pdf-core/
  pdf/                 PDF 加载、文字提取、渲染基础
  layout/              模型推理、检测结果解码、补框
  assign/              D 文字归属、分行分段、阅读序与配对
  pipeline.ts          单页处理的统一调用顺序
  document-flow.ts     按页接收结果，管理已确定内容与末尾接续组

src/entrypoints/pdf-translate/
  main.ts              产品入口与现有界面
  modules/translate/   翻译服务接入与请求调度
  modules/viewer/      现有译文定位与排版
  export/              现有导出

tools/pdf-verify/
  src/                 验证入口、界面、评分展示和切片读写
  dev/                 离线验证脚本、夹具与诊断资料
  slices/              原项目切片数据
  archive/             仍有留存价值的静态诊断报告
  wxt.config.ts        验证工具独立构建配置

model-store/
  doclayout_yolo.onnx  两种构建读取的同一份本地模型
```

正式入口与验证入口都直接导入 `src/modules/pdf-core/`。验证工具不再复制算法，不通过产品界面的 DOM 或调试日志反推算法结果。

共用核心可以使用 PDF.js、Canvas 和 ONNX Runtime；不要求全部变成脱离浏览器的纯函数。文字归属、阅读序、配对和文档顺序状态应可在无产品界面的测试中运行。核心不导入翻译计费、验证面板、目录选择器或产品 DOM。

### 3.2 两种构建

保留现有正式扩展命令。增加验证器的开发、构建命令，使用独立的入口目录、public 来源、WXT 生成目录和输出目录。验证器仍作为开发用浏览器扩展运行，接近当前环境，保留目录选择和 GPU/WASM 验证能力。

依赖版本由 MeowTabby 统一管理；验证工具不另养一套运行依赖。具体 WXT 根目录、源码引用和类型检查接线通过一次最小构建核实，不能只凭目录位置判断隔离成功。

正式构建需要同时满足：

- 入口发现范围不包含 `tools/pdf-verify/`。
- 正式入口的导入链不引用验证工具。
- 验证切片、样本、诊断报告和专用静态资源不进入正式 `public/`。
- 正式 ZIP 的安装产物无验证页面、专用脚本和数据。
- 单独检查源码 ZIP。当前 `zip.includeSources` 范围较广，安装包隔离不等于源码压缩包已隔离。
- 连续执行验证构建、正式构建，以及反向执行，均不发生资源残留或输出目录覆盖。

共用 PDF 核心和扩展运行所需的 PDF.js/ONNX 资源正常进入正式安装包。

### 3.3 模型与运行资源

共用模型推理实现，模型来源和进度通知由入口提供。产品继续支持现有下载、缓存、进度和可选内置模型；验证器保留内置模型、强制 WASM 运行方式及切片复用。

两边使用同一模型文件时记录其校验值。Worker、字库、CMap、WASM 和胶水脚本从统一资源源文件提供给各自构建，不复制维护。验证器内置模型不得导致默认正式构建自动带入模型；正式带模型构建继续遵循现有显式开关。

## 4. 唯一的 D 处理流程

### 4.1 固定 D 的实际行为

从原验证器 D 路径提取执行顺序，固定为唯一实现：

1. 获取 PDF 页及文字项，保留文字内容流顺序和可见页原点处理。
2. 获取检测结果。正常运行执行模型推理，验证切片模式读取原始检测结果。
3. 统一文字与检测框坐标；保留 MeowTabby 已有旋转页能力，两个入口使用同一适配。
4. 补框，文字归属、分行分段启用 D 的悬挂断段；漂浮段过滤沿用 D 实际调用的口径。
5. 阅读序保留公式扩宽限制：独立公式每侧扩宽限制使用当前实现的 `0.155 × 页宽`。
6. 按页码连接阅读序，统一执行 D 的扁平正文配对。

归属、分行、分段在当前 `assignItems` 内部相互关联，迁移时不为了让目录对应流程名称而强行拆开或改变执行顺序。

D 配对使用当前修改后的分值：`widthNear = 10`、`tailNoSentenceEnd = 15`，其余有效分值保持当前 D；阈值为 `49`。句末硬停、同页同栏筛选、多段块入组后断链等行为按 D 保留。

### 4.2 类别与显示口径

- 阅读序节点为除 skip 外的全部有检测框块，包括图、表、公式等 keep 块；无框 orphan 不进入阅读序图。
- 阅读序编号只给正文和标题，跨页连续编号；其他类别仍按现有验证功能显示。
- 同段配对只针对有段落的 `plain text` 翻译块；标题、题注等按 D 现有规则处理，不额外改变其断链行为。
- 阅读序使用的检测框、公式扩宽矩形，与译文定位的段落包络是不同用途的数据，不能相互覆盖。
- 正式渲染和送翻资格不能直接等同于“有阅读序编号”。非配对段落保留现有产品所需的正常翻译路径；未排序或无法定位的内容必须明确记录，不能静默丢弃。

### 4.3 删除旧路径

删除旧阅读序、旧配对流程、方案选择参数和多方案结果缓存。D 依赖的有效算法成为唯一默认路径，不再依靠实验开关启用。

删除 MeowTabby 旧页内配对、页首尾选取和旧跨页裁定接线。保留并改造的是等待状态与排版连接，而非旧合并判断。

删除旧方案专用测试，将仍有价值的文字、几何和排版回归迁移到新核心。不能通过保留旧 API 空壳或禁用现有测试掩盖未迁移的调用。

## 5. 按页推进与边处理边翻译

### 5.1 顺序是文档状态的约束

文档处理从第 1 页开始，按页码连续推进。滚动不得改变识别或送翻顺序。显示大图可以继续按可见范围绘制；算法需要的推理画布可在单页使用后释放，避免为了按序识别而长期保存整本书的高分辨率画布。

共用文档状态区分：已处理页、已确定单元、末尾待接续组、因该组而等待提交的后续单元。后续页面仍可继续识别，以确定接续关系。

“已确定”的含义是：再追加页面不会改变该单元的段落成员、顺序或送翻文本。不能简单地把当前 `planFlatMerges` 返回的末组全部视为最终结果。

### 5.2 单元与页批次

每个送翻单元保留成员的原始位置：页码、块标识、段落标识、阅读位置、原文和段落矩形。标识在本次分析版本内稳定，不再依赖“当前渲染过滤后第几个盒子”。

页内不同段落仍可并行。单元按页码组织批次，同一页内按 D 阅读序发起，缺少阅读序节点的保留翻译内容按现有确定顺序接入，不影响 D 的配对序列。页批次可以拆开提交，例如先提交第 1 页已确定前文，再提交稍后确定的第 1 页末尾跨页组。

跨页组以首成员页码和该成员的阅读位置作为送出位置；它只有一条翻译请求，各成员不再单独送翻。后续页已经入组的成员从各自普通请求中剔除。

保留最多两批翻译任务在途。批次按顺序发起，响应可以乱序完成，并按单元引用回填。这里限制的是批次并发，不把一个跨三页的组错误算成三个独立请求。

### 5.3 等待规则

例如第 1 页前 7 段确定、第 8 段可能接续：

1. 前 7 段立即送翻，第 8 段透明占位。
2. 处理第 2 页。若其首段接上且组已结束，先提交跨页组，再提交第 2 页后面的内容。
3. 若组继续接第 3 页，就继续识别第 3 页；不能让第 2 页排在该组后面的标题、题注或其他正文越过它。
4. 若第 2 页不接续，先把第 1 页末尾释放成最终单元，再提交第 2 页。
5. 到文件结尾，明确结束剩余等待并提交，不依赖下一页事件触发。

同一块包含等待段和其他段时，构造请求必须按等待边界拆开，不能因为“整块一次送翻”把等待段混进前文请求，也不能把后文提前提交。

实现应以“全量 D 结果”和“按页增量结果”的一致性测试证明可提前提交的边界。可先保留待定后缀重新计算，禁止每次新增一页都重建全部已送翻请求。

### 5.4 异常与重放

这是本方案补充的工程处理约定：

- 某页提取、推理或排序失败，停止越过该页的正常送翻并显示失败页码；此前已确认内容可继续返回，待定内容保留原文。不能把失败页当作不存在后合并两侧正文。重新加载后可重新处理。
- 已成功分析但没有配对候选的页面，与分析失败页面区别处理；是否跨越前者接续由 D 原有规则决定，不能擅自加断链规则。
- 阅读序 `placed < total` 明确报告，受影响的未确定内容不冒充完整结果送出，不自动切回旧算法。
- 翻译请求失败继续沿用现有失败隔离和重试口径，不阻止后续已确定批次按序发起。
- 筛选或翻译设置变化触发现有重放流程时，使用分析/翻译版本号识别新一轮结果；旧响应不能写入新页面或污染新设置的缓存。缓存仍可按现有规则复用，失效时机与当前产品含义一致。
- 导出、刷新、筛选均走同一个顺序控制入口，不直接另开 `processPage` 队列。

## 6. 译文原位回填

### 6.1 保留包络与簇盒规则

使用 D 输出的段落 `x/y/w/h`，按现有 `clusterParas` 和 `unionBox` 形成译文盒。D 改变分行、分段时，包络数值相应变化；分簇、标题单簇及包络生成规则不另换一套。

检测框用于检测、归属及阅读序；译文的基础位置来自文字行、段包络。跨页、跨栏成员各自保留原位盒，不生成跨栏大盒，也不把多页坐标求并集。

### 6.2 保留现有容量分配

合并组按成员顺序拼原文，统一送翻后，继续用现有 `splitByCapacity` 分配译文：末盒高度锁定原位高，前盒使用现有障碍约束下的可用高度；放不下则统一降字号，并保留现有行高、溢出和回填后的复核规则。

连接层统一接收可跨多页的成员列表，逐成员解析页码、段落和目标簇盒。普通段、标题、组成员的请求保持互斥，每段原文恰好归一个最终单元。组内任一目标无法解析时必须记录并按不漏翻规则处理，不能先剔除普通段请求再静默丢掉整组。

等待中的组成员强制独簇并透明占位；确定后回填各自位置并恢复原有底色。不因修改合并成员而清空相邻已翻译段落。

旋转页仍通过现有显示变换放回对应位置；核心坐标适配和产品显示变换只在各自边界执行一次，避免重复平移或旋转。

## 7. 内部验证工具与资料迁移

### 7.1 保留与删除

保留文件选择、拖入 PDF、重新选择、逐页进度、原框/补框切换、段落框、阅读序编号、组颜色、组成员摘抄、逐项评分、失败配对、排序异常提示、切片读写、离线验证脚本及必要数据。

验证工具直接展示共用核心返回的页结果、配对记录、最终组和等待组。新增页面时，等待组可以扩展，已确定组不得被重新解释。上述等待状态接入现有状态区，不向产品界面增加方案选择或开发入口。

删除旧/A/B/C/D 选择器、B/C 差异列表、C/D 新增断段统计及其专用计算。D 成为唯一实现后，不再额外执行不启用悬挂断段的第二次文字归属。

### 7.2 切片、脚本和历史资料

迁移现有切片 JSON、测试夹具、有效脚本和仍有留存价值的诊断报告。旧方案静态报告如保留，仅作为历史资料，不附带可运行的旧算法，也不作为正式构建输入。

切片仍保存原始检测结果，读取后走同一份 D 后处理。迁移保持现有文件格式可读；若模型、预处理或检测参数改变，必须使不匹配切片失效，不能把旧模型切片当成新模型输出。

迁入的切片目录仍名为 `slices`。验证器扩展来源改变后，旧 IndexedDB 保存的目录授权不会自动迁移，需要通过现有目录选择操作重新授权；数据文件本身仍可复用。提示文字改为新位置。

更新脚本中原项目的绝对路径、源码导入、构建输出位置和扩展 ID 查找。验收时禁用原项目路径，证明脚本实际使用新目录。外部 PDF 样本与 Python/docling 等参考环境列清依赖；不把历史脚本中的本机路径视为已迁入的数据。

不迁移依赖安装目录、浏览器配置目录、截图缓存、编译输出和增量编译文件；由新命令重建。删除原目录前对未追踪及忽略文件单独盘点，有价值的资料不能因未被 Git 跟踪而丢失。

## 8. 实施阶段与验收

### 8.1 阶段一：固定 D 基线

记录源提交与资源校验值，显式运行原验证器 D，使用现有样本、切片和测试夹具，保存逐页文字归属、段落及其包络、阅读序、编号、配对决定和组成员作为对照。对照运行关闭切片时，区分模型推理差异与算法迁移差异。

交付：可重复运行的 D 基线；尚不替换产品入口。

### 8.2 阶段二：建立共用核心和独立验证构建

抽取 D 的真实执行路径，删除旧方案分支；迁入验证界面和必要资源，接入同一核心。模型来源、运行资源和切片适配留在明确边界。

验收：相同文字与检测输入下，迁移前 D 与新核心的文字、包络、阅读序、配对决定和最终组合一致；两种构建输出互不污染。现有 D 夹具可独立运行。

### 8.3 阶段三：建立按页增量状态和送翻队列

先用可控假翻译器测试请求发出顺序和返回顺序，再接实际翻译入口。关键测试包括：

- 从第 1 页滚到第 10 页仍按页推进。
- 上页尾段不接续、跨两页、跨三页及连续多页接续。
- 等待组后有标题、题注、普通正文，同一块内有已确定与等待段。
- 末页收尾、空白页、无正文候选页、失败页、排序未完成。
- 页内多请求、两批在途、缓存命中、在途去重及单条失败。
- 增量最终组与整份输入一次执行 D 的组一致；已确定前缀不因后续页到达而变化。

验收：无请求越过等待组、无重复送翻、无永久挂起；请求可按序发起、响应可乱序回填。

### 8.4 阶段四：替换产品旧核心并接入原位排版

让 MeowTabby 调用共用页处理及文档状态；用多页成员引用连接现有簇盒和容量分配。移除旧合并裁定和对应孤立代码，迁移相关回归测试。

使用固定译文验证位置与容量，避免网络译文变化掩盖排版问题；再做实际翻译联调，检查现有计费通道和请求参数未变。

验收：单段、标题、跨栏组、多页组、旋转页、长译文、刷新、筛选及导出均可用。每段原文仅归一个单元，组成员全部回填正确页和位置。

### 8.5 阶段五：迁移资料并检查发行产物

迁移脚本、切片与必要资料，记录原项目可恢复备份。正式构建、验证构建分别运行并检查实际产物，检查 Chromium、Edge、Firefox 的现有构建目标及运行限制。

所有测试带 `SKIP_FREE_API=true`。提交代码前运行全量 `pnpm lint`，并运行受影响 PDF 测试、完整测试及正式/验证构建；记录原有失败与新增失败，不能把未运行的检查写成通过。

针对构建产物自动断言：无验证 HTML、专用脚本、切片和诊断数据；默认正式构建无验证器内置模型残留；源码 ZIP 按约定排除内部工具。通过文件清单和导入关系双重核实，不能只搜索单个项目名称。

## 9. 原项目退出与完成标准

完成合并应满足：

- 正式扩展和验证工具共享一份 D 核心及文档增量流程，无运行中的旧/A/B/C 路径。
- MeowTabby 产品界面与交互保留，定位、容量分配和导出符合本方案。
- 请求按页码和等待边界提交；追加页不重翻已确定内容。
- 验证器全部保留功能可在 MeowTabby 内启动，算法结果与正式扩展一致。
- 不存在指向原 pdf-verify 目录的运行或测试依赖。
- 正式发行产物不包含验证工具及专用资料。
- 原项目的切片、必要资料、未追踪文件和 Git 历史均已盘点并妥善保存。

原项目作为对照保留，不直接删除。实施完成后先把原目录移出运行位置并复验，证明不再依赖它。原项目 `.git` 按工作区规则保留，可将整个旧仓库移到归档位置；若用户最终要求释放工作区目录，应先明确备份的恢复方法，再处理原路径，不执行直接递归删除仓库的清理。

Git 提交仅在用户明确授权后执行，提交信息使用中文。用户已明确跳过单独的实施计划，执行及验收按本文各阶段推进。
